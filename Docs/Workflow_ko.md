# Ssalmuk 개발 워크플로우

## 목적

Ssalmuk은 별도 저장소 `1hwai/Ssalmuk`에서 관리하는 가벼운 브라우저 오목 게임이다. 기본 방향은 정적 HTML/CSS/JavaScript, 별도 빌드 과정과 로그인 없이 즉시 실행하는 것이다. 현재 게임 규칙이나 배포 구조를 바꾸는 일은 목표와 근거를 먼저 확인하고 진행한다.

이 문서는 작업 범위, 검증, 체크리스트, Git 절차의 기준이다.

## 필수 Skill

코드를 계획하거나 수정하거나 디버깅하거나 완료를 보고하기 전에 다음 두 파일을 읽고 따른다.

1. `.agents/skills/ssalmuk-engineering/SKILL.md`
2. `.agents/skills/verification-evidence/SKILL.md`

두 파일은 각각 작업 범위·구현 원칙과 검증 증거 기준을 정의한다. 이 문서와 충돌하는 상황이 생기면 임의로 무시하지 말고 먼저 충돌을 설명하고 해결 기준을 정한다.

## 기본 원칙

- **근거 먼저:** 재현, 소스, 브라우저 콘솔, 테스트 결과를 바탕으로 원인을 판단한다. 확인하지 않은 가설을 사실처럼 말하지 않는다.
- **범위 먼저:** 요청한 결과와 변경 허용 파일을 정한 뒤 구현한다.
- **최소 변경:** 관계없는 리팩터링, 디자인 변경, 의존성 추가를 끼워 넣지 않는다.
- **실제 동작 검증:** 코드가 그럴듯하거나 문법 검사가 통과했다는 이유만으로 기능 완료를 선언하지 않는다.
- **문서와 실제 상태 일치:** 체크리스트와 완료 보고는 실제 구현 및 검증 결과를 반영한다.
- **사용자 변경 보존:** 작업 전 Git 상태와 diff를 확인한다. 사용자 변경을 덮어쓰거나 확인 없이 초기화하지 않는다.

## 작업 절차

### 1. 현황 확인

작업을 시작할 때 저장소 상태와 관련 코드를 확인한다.

```bash
git status --short --branch
git remote -v
git log -5 --oneline
```

필요한 파일만 읽는다. 문제가 재현되지 않거나 근거가 부족하면 구현부터 하지 말고 확인 절차를 먼저 진행한다.

### 2. 작업 단위와 범위 선언

각 작업은 번호가 있는 단위로 기록한다. 예: `0-1`, `1-1`, `1-2`.

작업 전에 다음을 적는다.

- **목표:** 사용자가 관찰할 수 있는 결과
- **변경 허용 파일:** 정확한 경로
- **변경 제외 파일:** 이번 작업에서 건드리지 않을 경로
- **완료 조건:** 무엇이 참이어야 하는가
- **검증 방법:** 완료 조건을 실제로 확인할 명령 또는 브라우저 동작

여러 기능을 한 번에 묶지 않는다. 범위를 넓혀야 할 이유가 생기면 먼저 설명하고 범위를 다시 정한다.

### 3. 설계와 구현

- 기존 구조와 코드 스타일을 우선한다.
- 현재 기본 구조는 정적 HTML/CSS/JavaScript다. 프레임워크, 서버, 패키지, 빌드 도구를 필요 없이 추가하지 않는다.
- 오목 규칙, 턴 상태, AI 동작, 무르기, 재시작, 모드 전환을 수정할 때는 서로 영향을 주는 상태 변수를 함께 살핀다.
- UI 변경은 좁은 화면, 키보드 조작, 접근성 라벨에 미치는 영향도 고려한다.
- 구현이 요구사항이나 기존 동작과 충돌하면 조용히 동작을 바꾸지 말고 먼저 설명한다.

### 4. 검증

변경 내용에 맞는 검증을 선택하고, 마지막 수정 이후 새로 실행한다.

가능한 검증 예시:

```bash
node --check game.js
git diff --check
```

이 명령들은 각각 JavaScript 문법과 diff의 공백 오류 등을 확인할 뿐, 게임 전체의 동작을 증명하지는 않는다. 동작 변경 시에는 관련 브라우저 확인이나 독립적인 테스트도 수행한다.

필요에 따라 확인할 항목:

- 가로·세로·양쪽 대각선의 승리 판정
- 이미 놓인 칸과 게임 종료 후 착수 방지
- 흑/백 턴 전환 및 AI의 응수
- 1인 모드와 2인 모드의 무르기 동작
- 새 게임, 메뉴 복귀, 승리, 무승부 상태
- 모바일 화면에서의 보드 크기와 조작
- 브라우저 콘솔 오류

변경과 관계없는 항목까지 전부 검사했다고 주장하지 않는다. 실행할 수 없는 검증은 그 이유와 미검증 범위를 보고한다.

### 5. 체크리스트 갱신

작업 단위는 다음 형식으로 기록한다.

- [ ] `1-1` 목표와 변경 범위 확정
- [ ] 구현 완료
- [ ] 필수 검증을 마지막 수정 이후 다시 실행
- [ ] 결과와 제한 사항 확인
- [ ] diff 검토 및 커밋

검증 증거가 없으면 완료 항목을 `[x]`로 바꾸지 않는다. 이후 수정으로 검증이 무효가 되면 해당 항목을 다시 연다.

### 6. Git 및 커밋

커밋 전에 다음을 실행하고 결과를 검토한다.

```bash
git status --short
git diff --check
git diff
```

그 뒤 작업에 필요한 검증을 다시 실행한다. 변경 파일이 요청한 범위와 일치할 때만 커밋한다. 커밋 메시지는 실제로 끝난 변경을 설명해야 한다.

브랜치나 원격 상태가 불분명하면 `push`, `reset`, 강제 푸시 같은 이력 변경 명령을 먼저 실행하지 않는다. 새 브랜치를 만드는 것이 목적이 아니라면 불필요하게 브랜치를 늘리지 않는다.

### 7. 완료 보고

작업 결과를 보고할 때 다음을 분명히 적는다.

- 변경한 내용과 파일
- 실행한 검증 명령 또는 브라우저 확인
- 실제 결과
- 아직 확인하지 못한 사항이나 알려진 한계
- 커밋 SHA(커밋한 경우)

검증하지 않은 동작은 완료했다고 말하지 않는다.

## 현재 프로젝트 기준

- 저장소: `https://github.com/1hwai/Ssalmuk`
- 기본 브랜치: `main`
- 현재 형태: 정적 웹 게임
- 기본 실행: `index.html`을 브라우저에서 열기
- 기본 모드: AI와 1인 플레이, 같은 기기에서 2인 플레이
- 서버·로그인·빌드 과정: 현재 필수 아님
- 배포를 변경할 때: 실제 설정과 배포 결과를 확인하고 문서를 갱신한다.
